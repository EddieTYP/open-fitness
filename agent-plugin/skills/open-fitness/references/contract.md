# Open Fitness agent contract

The snapshot response includes `contractVersion`. Version `6` exposes typed
today-plan decision, adjustment, phase kind, duration range, confidence, and a
nullable request-scoped venue instead of localized decision fields. It also
allows `UiText.params` values to contain nested `UiText` descriptors so curated
exercise display labels can resolve in the selected locale. Raw workout,
template, correction, and selection exercise values remain strings.

Version `6` also treats strength sessions on the same local date with the same
non-null training block, phase, and session intent as one review occurrence.
For a split occurrence, `dashboard.latestStrength` contains aggregate duration,
set count, volume, and compatible optional totals rather than one session's
metrics. `dashboard.latestReview.overview` describes the aggregate and
`dashboard.latestReview.segments` lists each source session; consumers must use
the segments instead of treating `latestStrength.sessionId` as the sole source
entity. A single-session review keeps `overview` null and `segments` empty.

Presentation copy generated by Open Fitness is locale-neutral in the snapshot.
Fields such as plan briefing, course labels and guidance, session review, and
progress commentary use `UiText`: `{ "kind": "message", "key": "...",
"params": { ... } }`. Recorded or authored wording uses
`{ "kind": "source", "text": "..." }` and must be preserved verbatim. The
Web UI resolves message keys in the selected locale; agents should treat the
message form as structured facts and must not overwrite source text merely to
match the UI language.

The profile `preferredLocale` returned by `snapshot` is authoritative for new
titles, summaries, notes, and assumptions that an agent composes for storage.
The agent's chat reply may follow the language used in the current conversation.
Exact wording explicitly chosen by the owner, brands, product names, and direct
importer source fields remain verbatim. When an agent interprets a screenshot,
photo, or copied export, it composes user-facing fields in `preferredLocale` and
retains the raw wording only in a supported source/evidence field. Source text
is never a reason to put an agent-composed display field in another language. A
later locale change does not rewrite stored history.

The optional local stdio MCP exposes only `fitness_read` and `fitness_write` to
an MCP client. A client may display qualified or namespaced forms of those tool
names. The host agent or transport adapter is responsible for sender
authorization, model and image-input policy, tool allowlisting, and passing the
API settings only to the MCP subprocess. Neither setting appears in
model-visible tool arguments or results.

The plugin Skill is the operating contract. A generic MCP client that has not
loaded the Skill begins with resource `instructions`; it is a bounded fixed
local workflow and cannot read an arbitrary path or call the Fitness API.
Before composing a write, read resource `write_contract` with the exact
intended operation. That bounded card is the canonical model-facing body
shape. The connector independently performs canonical validation, preflight,
idempotency, at most one mutation, and authoritative verification for each
self-contained call. Read `evidence_reference` only when coaching or evidence
reasoning needs it.

Choose a named read `resource` or write `operation` and pass structured tool
arguments to the applicable tool; never construct JSON in shell syntax.
`fitness_write` returns `validated` for the non-mutating workout validator. For
a mutation it performs one write and its verification, then returns one
authoritative outcome: `succeeded`, `conflict`, `failed`, or `uncertain`. The
MCP connector generates a `requestId` and sends it as the `X-Idempotency-Key`
header; the API server validates and records that key. Retry the exact body at
most once with that same ID only after an `uncertain` outcome whose
`retryable` field is `true`.

For analysis, use dates in the profile timezone returned by the current
snapshot. The range must be ascending and no more than 120 days; default to at
most 84. Treat `dataCutoff` as the evidence cutoff. The
default view removes null attributes, audit/provenance metadata, bibliography,
data policies, low-signal segmental BIA fields, and aliases unrelated to the
returned workouts. It keeps effective operating-constraint IDs because they
are required for an explicit status correction, while raw constraint history
stays full-view only. The full view retains all non-null fields; neither view
changes the underlying API or SQLite records.

## Universal write sequence

1. Read `write_contract` for the exact intended operation, then read only the
   logical entity, duplicate candidates, exact units, and current
   revision/version named by that card. A generic client without the plugin
   Skill reads `instructions` once before this sequence.
2. If the agent will compose persisted text, read `snapshot` and use the
   profile `preferredLocale`. Preserve exact owner-chosen wording and
   brand/product names. For interpreted external evidence, keep raw wording only
   in a supported source/evidence field. Missing data stays absent or `null`.
   A configured owner-default venue applies when venue is omitted; an explicit
   venue overrides it, and an explicit unknown/not-applicable venue stays null.
   Without a configured default, do not infer one.
3. Incorporate any user steer received before dispatch into that one intended
   mutation.
4. Call the documented `fitness_write` operation once and retain its returned
   `requestId` and outcome.
5. Refresh a small read view only when it is needed for subsequent advice or a
   new decision, not to verify the mutation again.

Outcome handling:

- `validated`: the requested validation completed without a mutation. It never
  authorizes a save acknowledgement.
- `succeeded`: the mutation passed connector-owned verification. Reply with a
  natural brief acknowledgement; do not echo internal mutation details.
- `conflict`: stop and re-read the named current state. Deliberately revise,
  void, or abandon only after resolving the conflict; never guess a replacement
  value or replay stale evidence.
- `failed`: stop and report the returned safe error information. Correct a
  future request only from available evidence or explicit owner input; do not
  probe with guessed aliases or values.
- `uncertain`: do not claim success or send a compensating mutation. Retry only
  when `retryable` is `true`, using the exact same body once with the same
  `requestId`. When `retryable` is `false`, or if the retry remains uncertain,
  report that state and stop.

If the owner changes facts after dispatch, first honor the returned outcome.
After `succeeded`, use the supported update or correction for that same entity;
do not create a duplicate record.

## Workouts and progress

Before the first workout write in a session, successfully read
`workout_contract` and obey its machine-readable contract. Also read the
current `snapshot`. If parallel reads fail, retry each failed resource once
sequentially; a successful response from only one resource is not enough to
write. Required workout fields are `title`, `type`, `startedAt` with timezone,
`durationSeconds`, `sessionIntent`, and `sets`. `sessionIntent` is `normal`,
`deload`, or `test`; ordinary records use `normal`. Preserve session-level
effort in `effortRaw` and do not copy it to every set. Top-level `notesManual` stores a session note. A
note belonging to one set uses `coachNote`; set classification uses
`setTypeManual`. Keep set ordinals sequential and retain supplied load, reps,
time, distance, rest, set type, venue, RIR/RPE, pain, and notes. When venue is
not supplied, leave it absent or `null`.
The connector also accepts one deterministic grouped import shape:
`exercises[].exerciseName` with nested `sets[]`; it maps `exerciseName` to each
canonical set's `exercise`, `setNumber` to `setNoExercise`, and `weightKg` to
`weightKgReported`. It also
maps the unambiguous response aliases `sessionTitle` and `sessionType` to `title`
and `type`. Optional `endedAt`, `totalSetsReported`, and `trainingBlockId` are
assertions checked against the canonical time, flattened set count, and the
active block returned by the current snapshot. A payload that mixes grouped and
canonical sets or contains conflicting aliases or assertions is rejected.

Before writing a completed workout that belongs to a configured cycle, read
`snapshot` and the current `workout_contract` as needed, then include the
returned phase's current `trainingPhaseId`. If it is omitted, the API stores
one only when the title matches a single phase unambiguously; never invent an
ID. After a `succeeded` `workout_create`, refresh `snapshot` only when describing
phase advancement. Do not claim that the next phase is active unless the
verified association and Today/cycle result match. For a backdated workout,
use explicit user/source phase evidence and the returned stable ID; if phase
association remains unresolved, ask rather than claim advancement.

- Validate a complex payload without writing only when useful:
  `workout_validate`.
- Create: `workout_create`.
- Whole-session recovery: `workout_update` with `sessionId`,
  `action: "void"|"restore"`, and a specific `reason`.
- Daily/recovery note: `session_note_create` with `noteDate`, `noteType`,
  `note`, and applicable `sessionId`, `venue`, `exerciseOrArea`, or `pain010`.
  For a structured training cycle, link a recovery-status note to the relevant
  workout with `sessionId` when possible. Otherwise use a concise structured
  `exerciseOrArea` that matches the affected configured routine item; free-form
  prose alone does not scope a recovery adjustment to every training phase.

The successful reply must still be useful in a fresh chat: give one meaningful
comparison against the previous same-phase or planned reference and one
next-session target. Use the pre-write snapshot plan/reference plus the verified
mutation result first. Fetch the narrowest useful `analysis` range only for a
backdated or phase-mismatched workout, or when that snapshot has no comparable
reference. Do not expand this into a full report. Report factual changes before
interpreting them. In particular, a higher load with fewer reps does not
establish improved overall performance when comparable RIR/RPE or form evidence
is missing; use a conditional next target instead.

Optional coaching detail never blocks a valid completed-workout write after all
contract-required fields and any required phase scope are resolved. Submit the
supplied workout first and require `succeeded`. The same reply must already
provide a useful factual comparison and conservative next-session target. It
may then ask at
most one short optional follow-up only if the answer could materially refine
that already-given target, or the owner explicitly requests a progression
decision. Missing RIR alone is insufficient. The question must identify the
exact workout, exercise, and set so its answer can only refine, never replace,
the initial review. Once the owner answers, do not ask another optional question.

An answer inherits the narrow scope of the immediately preceding question. If
the agent asked how many reps remained on a named exercise's final set, a reply
such as “仲有兩下” is `RIR 2` for that exact set. Read the exact workout and its
current effective set value. If it is already `RIR 2`, make no write. Otherwise
call `correction_create` with `targetScope: "workout_set"`, that set's ID,
`fieldName: "effort_raw"`, the effective `originalValue` (including JSON `null`
when unset), and `correctedValue: "RIR 2"`. Require a `succeeded` outcome.
Never create a second workout, apply the answer to every set, or silently guess
a set when the preceding context is not unique. An unscoped reply must follow
the normal required correction-scope clarification rule, not this shortcut.

## Food items and completed meals

Search active and inactive foods before creating a reusable item. Creation is
`food_item_create` with `displayName`, optional `brand`, `baseQuantity`,
`baseUnit`, nested `nutrients`, and optional `sourceNote`.
Revision/deactivation/restore uses `food_item_update` and the latest record.
Historical meal snapshots must not change when a food version changes.

For completed meals use `meal_create` with a complete `items` array. A
registered item uses `foodId` and `quantity`. A one-off item uses its name,
`quantity`, `unit`, `assumption`, `confidence`, and a nested `nutrients` object.
For example: `{"name":"Tofu","quantity":150,"unit":"g","nutrients":{"energyKcal":120,"proteinG":12}}`.
On writes, the canonical field is always `name`; never copy the read-only
`itemNameSnapshot` field or invent `itemName`. The connector repairs either
alias only as a last-resort compatibility safeguard and rejects conflicts.
Do not use `amount` or place nutrient fields at the item top level.
`nutrients.energyKcal` is required for a one-off item. Track available protein,
fat, saturated/trans fat, carbohydrate, sugar, fibre, sodium, and cholesterol;
unavailable nutrients are `null`.

Use explicit `mealType`. If absent, the API may infer it from the profile's
local time and the reply must say so. `運動後` is `mealType: "other"`,
`contextTag: "post_workout"`, `originalMealType: "運動後"`.

Meal timing is semantic, not shared with the workout timestamp contract. Use
`timePrecision: "exact"` only when the owner or source supplied the timestamp.
When relative wording such as “just now” supplies enough context to derive an
`eatenAt` timestamp from the current turn, use `timePrecision: "inferred"`.
When only the date is known, send `eatenAt: null` with
`timePrecision: "date_only"`. Never use the workout-only `minute` value for a
meal. The MCP conservatively repairs `minute` to `inferred` only when an
`eatenAt` timestamp is present; without one it stops rather than inventing a
time.

A full correction uses `meal_update` with top-level `mealId`, current
`expectedRevisionNo`, the complete replacement meal fields, and the full
`items` array. Do not nest the replacement under a `meal` key and do not add an
`action`; the MCP routes this shape to the full-revision endpoint. A targeted
quantity, classification, or registered-food addition also uses `meal_update`,
but must set `action` to `quantity`, `classification`, or `append_food` and
include that action's current-revision fields. Soft-delete/undo uses
`meal_delete` with the documented whole-meal/item action and current revision.
After `succeeded`, refresh the affected nutrition date only when current totals
or advice are needed.

## Plans, combinations, body, and energy

- Effective-dated calorie and protein targets use `nutrition_target_set` with
  `{ "effectiveFrom": "YYYY-MM-DD", "calorieTargetKcal": 2000,
  "proteinTargetG": 150 }`. Calories must be an integer from 500 through
  6,000; protein must be greater than 0 and at most 500 g. The calorie value is
  the final fixed daily intake target: Active Energy and estimated expenditure
  remain visible, but do not increase it. Read `nutrition_targets` first and
  require a `succeeded` write outcome. Older target rows whose explicit calorie
  target is null retain the legacy BMR-minus-deficit-plus-activity calculation.
- Formula review is never an automatic write. Read `nutrition_calibration`
  and `nutrition_targets`; the former returns only a bounded aggregate and the
  latter supplies the current `settingsId`. If the aggregate is ready, propose
  the exact `effectiveFrom`, integer `dailyDeficitKcal` (0–2,000),
  `activeEnergyCreditRate` (0–1), and `proteinTargetG`. Only after the owner
  explicitly confirms those values may `nutrition_formula_calibrate` write
  `{ "mode": "formula", "effectiveFrom": "YYYY-MM-DD",
  "dailyDeficitKcal": 400, "activeEnergyCreditRate": 0.8,
  "proteinTargetG": 150, "expectedSettingsId": "..." }`. A `conflict` outcome
  means the current rule changed: stop, re-read, and present a fresh proposal.
  Require the confirmed write to return `succeeded`.
- Pending food uses `plan_create`, `plan_update`, and `plan_delete`; it
  contributes nothing to intake until consumed. A multi-day repeat uses one
  `plan_create` call with `scheduledDates` and the complete per-date `items`
  array, rather than one write per date. A registered-food plan item expressed
  in the food version's native basis is `{ "foodId": "...", "quantity": 0.4 }`.
  When the owner reports a different compatible unit, include it explicitly,
  for example `{ "foodId": "...", "quantity": 194, "unit": "g" }`; the API
  performs the authoritative conversion against that food version's
  `baseQuantity` and `baseUnit`. Convert the owner's language into
  the canonical intent `targetDate`, `mealType`, `items`, and `action: add` in
  the profile timezone. Read `plans` without date arguments, then select the
  returned pending plans by exact `scheduledDate` and `mealType`. One match is
  revised by preserving its items and appending the requested items; no match
  is created with `plan_create`; multiple matches or an ambiguous date/meal
  type require clarification without a write. Read the current version before
  revise/consume/undo/cancel.
- Reusable combinations use `combo_create` or `combo_update`, active registered
  foods, a complete ordered item list, and optimistic versioning. Each input
  item uses `{ "foodId": "...", "quantity": 0.4 }` for the food version's
  native basis, or adds an explicit compatible `unit` when the owner reports a
  different measure. The API performs the authoritative conversion against
  that food version's `baseQuantity` and `baseUnit`. Read responses expose the
  saved quantity as `defaultQuantity`; do not copy that response field into a
  new request. The MCP connector repairs `defaultQuantity` for combination and
  plan items only when it is an unambiguous alias and rejects conflicting
  values.
- For an owner-confirmed meal-prep request such as splitting known ingredients
  into five portions for five named dates, create or reuse the registered
  ingredients, save one combination serving, then create the pending plans in
  one multi-date call using the same per-serving quantities. Do not record the
  portions as completed meals. Require `succeeded` for each intended mutation;
  after a partial failure, search first and resume only the missing steps rather
  than recreating successful food items.
- Body measurements use `body_measurement_create` with an explicit stable
  `measurementId`, exact timestamp, `source` data channel, `sourceDevice`
  measuring hardware, weight, and every supplied canonical field. A segmental
  export must preserve total and supplied
  segmental body-fat, muscle-mass, muscle-quality, BMR, and device values in
  the single create body and require a `succeeded` outcome.
  Read `profile` first only when its timezone or locale is needed to resolve a
  non-explicit measurement time; an exact ISO-8601 timestamp needs no profile
  pre-read.
  The succeeded envelope already includes the current measurement, comparison
  with the previous same-device measurement, and a bounded seven-day trend.
  Use those facts for the daily acknowledgement: provide one supported
  seven-day observation when `sevenDay.sufficient` is true, or briefly state
  that the trend is not yet sufficient. Do not read broad analysis or repeat
  the exact measurement readback. Use 7/28-day analysis only for an explicit
  formal trend review.
  `body_measurement_enrich` may fill missing extended fields on one exact
  existing record using
  `measurementId`, `expectedCreatedAt`, and `values`; it may replace only the
  default `Manual entry` device source or the default `Open Fitness WebApp`
  source with an explicit source, and cannot overwrite other non-null values.
  BIA values are trend estimates regardless of device.
- Supplied Active Energy uses `active_energy_create`. Current-day partial values
  are `provisional`; a complete historical daily total is `final` with
  `observedAt: null`. Never substitute workout-reported calories.
- Field-level append-only corrections use `correction_create`. Canonical
  workout targets are `targetScope: "workout_session"` with
  `fieldName: "session_title"` or `fieldName: "training_phase_id"`, and
  `targetScope: "workout_set"` with `fieldName: "exercise"`, `fieldName: "reps"`,
  `fieldName: "weight_kg_reported"`, or `fieldName: "effort_raw"`. Read the exact `workout` first,
  send its current effective field value as `originalValue`, and provide the
  field's typed `correctedValue`. `reps`, `weight_kg_reported`, and `effort_raw`
  may explicitly be corrected to `null`; `training_phase_id` is attach/reassign
  only and rejects a null corrected value, while an unassociated workout may use
  `originalValue: null`.
  The API validates each type/range, checks phase IDs against the current
  cycle, requires a valid target workout local date equal to `effectiveDate`,
  rejects stale originals and unknown fields, and leaves raw rows untouched. A
  set correction changes only that set; correct every intended set
  ID explicitly rather than assuming a session-wide rename. Require a
  `succeeded` outcome. The lean analysis view omits `setId`, so never build a set
  correction from that view alone. Use `training_phase_id` correction as the
  official path to associate an existing workout with a cycle phase; never edit
  SQLite directly.
- Operating constraints use the same append-only correction route with
  `targetScope: "operating_constraint"`, the exact `constraintId` returned by
  lean analysis as `targetKey`, and `fieldName: "status"`. Supported status
  values are `Paused`, `Conditional`, and `Resolved`. Send the current effective
  status as `originalValue`; the API rejects missing targets, stale originals,
  unsupported values, corrections dated before the source constraint, and
  non-monotonic replays. Only an explicit owner conclusion authorizes this
  transition. Do not promote ordinary pain/recovery prose into a constraint
  change. Require a `succeeded` outcome; use `view: "full"` only when the raw
  constraint/correction history is actually needed for subsequent advice.

The current personal working budget is the latest applicable stored rule, not
a hard-coded Skill fact. Read the nutrition day/targets before quoting calorie
or protein remaining. A non-null explicit calorie target is fixed; only legacy
rows with a null explicit value use the activity-adjusted formula. In a
`nutrition_today` response, `budget.basis` is the locale-neutral machine value
`fixed_daily_target`, `bmr_deficit_plus_active_energy`, or `null`; do not show
that code directly to the owner.

## Routine exercise selection

The rendered course for the current date is
`snapshot.dashboard.todayPlan`. It may be derived from corrected workout
history even when `snapshot.dashboard.trainingSchedule.cycle[].routine` is
empty; never infer that today's course is empty from the cycle template alone.

Read `training_exercises` for the owner's raw, deduplicated suggestions from
the current template, prior selections, and corrected non-voided workout
history. Pass the current snapshot item's `phaseId` and `slotId`; use
`same_slot`, `same_phase`, then `same_category` suggestions before `other`.
A one-date selection may use one of those names or an exact new name
supplied by the owner. Preserve its script, case, punctuation, and product or
machine wording; never fuzzy-merge two exercise variants or treat them as the
same progress line.

If the owner explicitly supplies a venue for this choice, read `snapshot` with
that exact `venue` argument before deciding or writing. Otherwise, a venue that
the owner deliberately configured in the selected agent may be passed as the
`venue` argument. Without either source the planning venue remains null.
Venue-scoped choices stay limited to the routine item's configured alternatives.

Use the `fitness_write` operation `training_exercise_select`. The body must include
`phaseId`, `slotId`, `exercise`, and one scope:

- `date`: add `date` from `snapshot.dashboard.todayPlan.planningDate`;
- `venue`: available only when `snapshot.dashboard.todayPlan.venue` is non-null;
  add that exact resolved value and never invent a venue;

Clear wording such as “today use X” is confirmation for that date-scoped write;
do not ask the owner to repeat the scope. If the request could mean either one
date or a permanent change, ask one short question. Permanent changes use the
full template workflow below, never a shortcut selection. A date selection
overrides a venue selection; a venue selection overrides the template. Require
the selection write to return `succeeded`.

## Course overrides

### Planned deload or test session

After the owner confirms today's intent and the complete prescription, use:

```json
{
  "scope": "planned_session",
  "phaseId": "<todayPlan.phaseId>",
  "date": "<todayPlan.planningDate>",
  "trainingBlockId": "<profile.currentTrainingBlock.blockId>",
  "sessionIntent": "deload",
  "expectedPlanFingerprint": "<todayPlan.planFingerprint>",
  "items": [
    {
      "slotId": "<todayPlan item slotId>",
      "exercise": "<todayPlan item exerciseKey>",
      "prescription": "2 × 5",
      "loadGuidance": "70 kg",
      "effort": "RIR 4"
    }
  ]
}
```

`sessionIntent` is `deload` or `test`. Include every working item exactly once
and provide the final prescription explicitly. The plan is limited to the exact
profile-local date, phase, and active block. A matching completed workout
consumes it; it cannot alter or be consumed by another date, phase, block, or
intent. Require the write to return `succeeded`.

### Date-scoped complete course

Use `fitness_write` operation `training_course_update` only after reading the
complete `snapshot.dashboard.todayPlan`. The request body is:

```json
{
  "scope": "date",
  "phaseId": "<todayPlan.phaseId>",
  "date": "<todayPlan.planningDate>",
  "expectedPlanFingerprint": "<todayPlan.planFingerprint>",
  "items": [
    {
      "slotId": "<todayPlan item slotId>",
      "exercise": "<todayPlan item exerciseKey>",
      "prescription": "2 × 5",
      "loadGuidance": "92.5 kg",
      "effort": "RIR 3-4"
    }
  ]
}
```

Include every working item with a `slotId` exactly once. The API rejects a
partial course, stale fingerprint, changed exercise, duplicate slot, or
unknown field. The saved values apply only to that profile-local date; the
template and workout history remain unchanged. Require the write to return
`succeeded`.

### Confirmed next-normal progression

Read `training_progression` with the completed phase's stable `phaseId`. It
compares only normal sessions in the active training block and returns either
bounded proposals or a blocked reason. Deload and test sessions advance the
cycle but never qualify as normal-load anchors or progression evidence. After a
deload, keep the last normal prescription for that phase and wait for the next
normal result before evaluating progression again.

Show the owner the proposed load or range and wait for explicit confirmation.
When no configured `loadIncrementKg` fits within the 2–10% range, retain the
range and do not invent a machine increment. A confirmed write is:

```json
{
  "scope": "next_normal_occurrence",
  "phaseId": "<training_progression.phaseId>",
  "trainingBlockId": "<training_progression.trainingBlock.blockId>",
  "sourceSessionId": "<proposal.sourceSessionIds[1]>",
  "expectedProgressionFingerprint": "<training_progression.progressionFingerprint>",
  "items": [
    {
      "slotId": "<proposal.slotId>",
      "exercise": "<proposal.exercise>",
      "prescription": "3 × 8-10",
      "loadGuidance": "62.5 kg",
      "effort": "RIR 2-3"
    }
  ]
}
```

Include only proposal items the owner confirmed. The override applies to the
next normal occurrence of that phase in the same block. A deload or test does
not consume it; completion of a normal session consumes it once. Re-read the
same `training_progression` resource after a conflict instead of reusing stale
evidence.

## Training block changes

When the owner asks for a different goal or prescription, ask whether it is a
one-session change or a persistent new training block. One-session changes use
a course override. For a persistent change, read `profile`, show the concise
goal and template diff, and wait for explicit confirmation. Then call
`training_block_start` with the latest profile revision:

```json
{
  "expectedUpdatedAt": "<profile.updatedAt>",
  "goalType": "endurance",
  "primaryGoal": "Improve muscular endurance",
  "trainingBlockChangeReason": "Owner changed the training goal",
  "trainingCycleConfig": { "version": 2, "phases": [] }
}
```

`trainingCycleConfig` is optional when the confirmed template stays unchanged.
The new block snapshots the effective template and ends the old block. It never
uses an older block as progression evidence; the first normal session in the
new prescription establishes its own anchor. A stale profile revision returns
`conflict` and requires a fresh read and confirmation.

## Full training template management

Read `training_template` to receive the current effective version-2 template,
its `profileUpdatedAt` revision, and a deterministic read-only proposal. The
proposal fills only empty training-day routines from the latest corrected,
non-voided strength session that can be mapped to that stable phase. It does
not invent alternatives or overwrite an existing routine, and it is never
permission to write. The proposal search is bounded to the 500 most recent raw
strength sessions. Review any proposal `warnings`; unsupported historical
names are omitted rather than rewritten or guessed, while valid routine items
beyond the 20-item phase cap are truncated with an explicit warning.

Before `training_template_update`, prepare the complete desired template and
show a concise item-level diff covering additions, removals, order, preferred
exercise, alternatives, sets, reps, and effort. Obtain explicit owner
confirmation for that exact diff. The body is:

```json
{
  "expectedUpdatedAt": "<profileUpdatedAt from the latest read>",
  "template": { "version": 2, "phases": [] }
}
```

Keep every existing phase ID and its kind unchanged. Labels, phase order, and
routine items may change; new stable phase IDs may be added. A stale revision
returns `conflict`: stop, re-read, recompute the diff, and ask again rather than
merging silently. In the same transaction, the server may attach stable phase
IDs to older unassigned workout sessions that match exactly one pre-change
phase; it does not rewrite their workout content. Require this write to return
`succeeded`, then reply with a natural short acknowledgement instead of echoing
mutation internals.

## Training schedule state

Treat `analysis.trainingSchedule.status` and
`snapshot.dashboard.trainingSchedule.status` as authoritative. When it is
`paused`, the snapshot's `todayPlan` is intentionally null. Do not describe the
day as a missed session, consume a cycle phase, or infer that the next strength
day was skipped. The pause may end on `pause.resumeOn` or by a later manual
resume event.

The MCP has no training-schedule mutation operation. Pause, resume, and day-off
changes stay in the Web UI; never approximate them with `session_note_create`,
`correction_create`, or agent memory.

# Internationalization contract

## Status

Open Fitness targets four first-class locales:

| Locale | Product language |
| --- | --- |
| `zh-HK` | Hong Kong Traditional Chinese, retaining the current Cantonese tone |
| `zh-TW` | Taiwan Traditional Chinese and Taiwan terminology |
| `zh-CN` | Mainland Simplified Chinese and Mainland terminology |
| `en` | Neutral English |

These are product and Web UI locales. Repository README editions are provided in
English, `zh-TW`, and `zh-CN`; no separate `zh-HK` README is maintained. Hong
Kong Traditional Chinese remains a first-class product and Web UI locale.

The locale resolver, persisted preference, shared formatters, primary UI, and
derived dashboard presentation support all four locales. Training plans,
session reviews, progress commentary, and log presentation cross the server
boundary as locale-neutral message descriptors. Stored source-authored content
remains verbatim by design and may therefore differ from the selected UI
language. New user-facing text composed by an agent for storage uses the profile
`preferredLocale` at composition time; the Web UI never retro-translates it.

## Non-negotiable boundaries

- Locale is presentation preference. Timezone determines record dates. Never
  infer one from the other.
- Stored enums, IDs, status codes, and API error codes remain stable ASCII.
- Switching locale never rewrites historical records.
- Never machine-translate arbitrary stored source text at display time. A
  curated, allowlisted canonical exercise identity may resolve to a localized
  display label without rewriting the saved value; unknown and custom names
  remain verbatim.
- An agent uses profile `preferredLocale` for new persisted titles, exercise
  labels, summaries, notes, and assumptions it composes. Its chat reply may
  follow the language used in the current conversation.
- Preserve exact wording explicitly chosen by the owner, brand/product names,
  and direct importer source fields. When an agent interprets a screenshot,
  photo, or copied export, retain raw wording only in a supported
  source/evidence field and compose user-facing fields in `preferredLocale`.
- User-created exercise names fall back to their saved text. Curated catalog
  entries may carry localized labels keyed by a stable exercise ID.
- API and domain behaviour must be invariant across all locales.

Content explicitly supplied and stored as entered includes profile goals,
cycle-day names, exercise and venue names, workout notes, food/brand names, meal
source text, constraints, decisions, evidence, and correction reasons.

## Authenticated API error contract

Authenticated API failures use one locale-neutral JSON envelope:

```json
{
  "errorCode": "STABLE_ASCII_CODE",
  "facts": {},
  "error": "Optional neutral compatibility text"
}
```

- `errorCode` matches `^[A-Z][A-Z0-9]*(?:_[A-Z0-9]+)*$` and is the only
  field clients use for branching.
- `facts` is always an object. Machine-readable conflict data such as current
  versions, supported values, field names, and target IDs belongs there rather
  than in completed prose.
- `error` is optional, ASCII, neutral compatibility text for older clients. It
  is never a localization surface and clients must not infer behaviour from it.
- `5xx` envelopes discard facts and internal exception messages and return only
  a safe code plus `Internal server error`. Full details remain server-side.
- This boundary applies only to failures. Successful owner- and source-authored
  values remain Unicode and are returned verbatim; do not ASCII-normalize names,
  notes, evidence, labels, brands, or imported source text.

`agent-plugin/skills/open-fitness/scripts/fitness-mcp.mjs` shapes analysis data only for a
successful response. For non-success JSON, it validates `errorCode` against the
same grammar and requires object-valued `facts`, then exposes those fields
directly in the MCP tool error result. Optional legacy `data.error` text is not
a decision key; a malformed non-success payload becomes the local
`FITNESS_API_INVALID_ERROR_ENVELOPE` failure. MCP contract fixtures cover 401,
400, 409, redacted 500, and Unicode success data.

## Lean architecture

The app does not need locale-prefixed routes or a large routing framework. Use a
small typed internal layer:

```text
lib/i18n/
  locales.ts
  catalog.ts
  format.ts
  request-locale.ts
  messages/
    common.ts
    exercises.ts
    fitness.ts
    log.ts
    nutrition.ts
    profile.ts
    index.ts
components/i18n/
  I18nProvider.tsx
  LocaleSelect.tsx
```

Required properties:

- `AppLocale = "zh-HK" | "zh-TW" | "zh-CN" | "en"`;
- one allowlisted resolver, compile-time per-fragment parity, and duplicate-key
  rejection when catalogs are assembled;
- a durable profile `preferredLocale`;
- a non-sensitive per-device cookie for pre-login and device override;
- shared locale-aware date, number, and unit formatters;
- only the selected catalog passed to the client tree.

Resolution order after profile setup is complete:

1. explicit device cookie;
2. owner profile preference;
3. compatible `Accept-Language` value;
4. `zh-HK` for upgraded installations.

Before setup is complete, the cookie and compatible `Accept-Language` value take
precedence so a new user can complete setup in their device language. Saving
the profile persists that selected locale.

## Semantic decoupling comes first

Visible copy currently leaks into business logic and API payloads. Before
translating the interface:

1. Replace decisions inferred from displayed words such as recovery or deload
   titles with explicit flags/enums.
2. Stop using localized meal labels as semantic discriminators; use stable
   context tags.
3. Return stable API error codes and localize them in the UI.
4. Return structured facts or `UiText` descriptors instead of completed
   server-side Cantonese sentences. `UiText` is either
   `{ kind: "message", key, params }` or `{ kind: "source", text }`.
5. Keep analysis endpoints locale-neutral and fact-oriented for agents.

This order prevents a wording change from changing training or nutrition
behaviour.

## Rollout

1. **Domain/API decoupling** — remove localized-string behaviour and introduce
   stable error/status codes.
2. **Locale foundation** — profile/cookie resolver, `<html lang>`, metadata,
   selector, and shared formatters.
3. **Static UI** — move all system chrome to typed catalogs; retain contextual
   HK, TW, CN, and English writing rather than character conversion.
4. **Derived presentation** — restructure dashboard, log, progress, and coaching
   prose into facts/message descriptors.
5. **Agent contract** — expose preferred locale and profile-local timezone while
   preserving source content.
6. **QA** — mobile/tablet/desktop rendering, English expansion, HK/TW/CN
   terminology review, accessibility labels, PWA metadata, and locale-invariant
   behaviour tests.

## Definition of four-language ready

- No raw system-facing copy is added outside the catalog allowlist.
- All four catalogs have identical keys and pass rendered smoke tests.
- Dates, numbers, and units use the selected locale and profile timezone.
- Login, errors, empty/loading states, metadata, and accessibility copy are
  localized.
- The same fixture produces identical domain decisions in every locale.
- English layouts do not overflow at supported mobile, tablet, and desktop
  widths.
- A native speaker has reviewed HK, TW, and CN terminology; automated script
  conversion alone is insufficient.
